### 税額計算

| 起きたこと | 原因 | 対策 |
|---|---|---|
| 所得税の1,800万〜4,000万円の区分が35%になっていた（正しくは40%） | 数値が一次情報で確かめられていなかった。控除額2,796,000円は40%のときの値で、表の中でも矛盾していた | 法定の数値を `taxRules.ts` に集め、国税庁のページから取得した表と手計算の両方で確かめる |
| 基礎控除が48万円で固定、復興特別所得税も端数処理もなかった | 年分ごとの税制という前提がなかった | 年分を引数に取る設計にした。令和2〜10年分に対応し、未公表の年分は暫定の扱いにした |
| 令和8年分の数値を記憶で入れそうになった | 最新の改正を確信を持って把握していなかった | 国税庁タックスアンサーのHTMLを取得し、表の構造（rowspan/colspan）を保ったまま読み取った |
| `a * 2.8` を `Math.floor` すると1円ずれることがある | 浮動小数点の誤差 | 整数で計算する（`(a * 28) / 10`） |
| 年度を切り替えると、前の年度の計算結果が新しい年度として保存された | 結果が年分に依存するようになったのに、画面が結果を残していた | 結果に `taxYear` を持たせ、年度を切り替えたら破棄し、保存時にも一致を確かめる |
| 実際の申告書と照合すると、税率・基礎控除・復興特別所得税・端数処理は一致したが、税額はアプリのほうが多かった | 損益通算、寄附金控除、税額控除、予定納税が未実装 | 今後の課題。**実際の申告書との照合は、計算の正しさを確かめるよい方法** |

### データベース（MongoDB / Mongoose）

| 起きたこと | 原因 | 対策 |
|---|---|---|
| 「年度ごとに1件」の一意インデックスが実際には作られていなかった | 既存のデータに重複があり、MongoDB がインデックスを作れなかった（エラーはログに出るだけ） | 重複を整理するスクリプト（dry-run、バックアップ、`--apply`）を作り、起動時に警告を出すようにした |
| 売却済み物件のレコードが1件あると、その年度の不動産所得一覧が丸ごと空になった | Mongoose のドキュメントを `{...doc}` で展開して値が失われ、例外を `catch` して `[]` を返していた | `.lean()` で取得し、エラーを握りつぶさない |
| 物件を売却済みにできなかった | 作成・更新APIが `saleStatus` と `saleDate` を無視していた | APIで受け付け、更新時にも `runValidators` で検証する |
| 不動産所得一覧の画面が404になっていた | 画面が呼ぶ `GET /:year` のルートが実装されていなかった（サービス層の関数だけあった） | ルートを追加し、ルートの統合テストを書いた |
| シードのデータがアプリから見えない | シードが別名のコレクション（`salary_income_records` など）に書き込み、`userId` も入れていない | **未対応**。シードはモデルを使って書き込むべき |

### テスト

| 起きたこと | 原因 | 対策 |
|---|---|---|
| 失敗しているテストの多くが、実装に存在しない関数を対象にしていた | 実装を読まずにテストを書いていた | 実装の公開APIに合わせて書き直した |
| 常に合格する検証があった（`expect(x \|\| true)`、`>= 0`、`if (isVisible)` の中だけの検証） | 失敗を消すために検証を緩めた | 禁止のルールにした（AGENTS.md）。**修正を外すと失敗することを確かめる** |
| E2E が実在の物件にテストデータを書き込み、開発用DBに数十件のゴミデータができた | E2E が開発用DBをそのまま使っていた | E2E専用のDBを Playwright が自分で使い、開発用のバックエンドが動いていれば止まるようにした。前後でDBのハッシュ値を比べて、変わらないことを確かめた |
| 実行するたびに違うE2Eのテストが落ちた | 初回起動時の案内のモーダルが、ボタンの上に重なってクリックを奪っていた | `beforeEach` で案内を完了済みにする |
| 給与のE2Eが、全体を実行したときだけ落ちた | 年度ごとに1件になったので、並行して動くテスト同士が互いのレコードを上書きした | そのspecは順番に実行する（`test.describe.configure({ mode: 'default' })`） |
| 削除のテストが何も削除していなかった | 確認ダイアログの承認処理を、クリックの後に登録していた | ダイアログの処理はクリックの前に登録し、件数が減ることを確かめる |

### リポジトリの構成

| 起きたこと | 原因 | 対策 |
|---|---|---|
| GitHub にフロントエンドのコードがなかった | `frontend/` が `.gitmodules` のないサブモジュールの参照で、リモートもなかった | 通常のディレクトリとして取り込んだ |
| README のドキュメントへのリンクが、存在しないファイルを指していた | ドキュメントの整理のときに更新されなかった | 実在するドキュメントを指すように直した |

### AIエージェントの作業の進め方

| 起きたこと | 原因 | 対策 |
|---|---|---|
| サブエージェントの報告に、誤りや検証の緩めが含まれていた（「テストを通した」が、検証を緩めて通していた、レビューの指摘の一部が事実と違った） | 報告をそのまま信用しそうになった | 報告は必ずコードとテスト結果で確かめる |
| 一時ファイルの削除を並行で実行し、そのファイルを使う処理より先に消えた（修正したコードを一時的に失った） | 依存関係のある処理を同時に実行した | 削除は、依存する処理がすべて終わってから行う |
| データを取り込む前に、既存の物件が登録されていることに気づいた | — | 取り込む前に既存のデータを確認し、重複や上書きについては利用者に確認する |
